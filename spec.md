# Spec: Screenlog

## Objective

Screenlog is a personal watch-logging app that keeps Letterboxd's movie logging/rating experience while giving **TV shows full, equal support** (shows are not a bolted-on afterthought — they get the same search/log/rate experience as movies).

**User story:** As a user, I want to search for movies and TV shows, rate them (both an overall rating for a show and a separate rating per season), optionally leave a written review, record when I watched something, and keep unwatched titles in a watchlist.

**Out of scope for MVP (deferred to v2):**
- Social features beyond public review attribution (following other users, activity feed, likes/comments on reviews) — the architecture will leave room for this later, but it won't be built now. The one exception, added after initial planning: every user's rating + review is publicly readable, attributed by username, under the relevant movie/show/season — see the RLS note below. This is read-only attribution, not a social graph.
- Custom lists (Letterboxd's "Lists" feature, e.g. "My Top Sci-Fi Movies").
- Episode-level logging — TV granularity is **show + season**, no episode level.
- ~~A browsable **public** profile page~~ — **now in scope, see [Post-MVP Features](#post-mvp-features) Feature 9.** Original MVP position: attribution stayed inline on the title's page only, and `/profile` was a **private** owner-only dashboard. Feature 9 reverses this: `/user/[username]` becomes a public profile visible to anyone, listing that user's logged movies/shows, favourites showcase, and counts.

**Definition of done:** A user can sign up and log in, search TMDB for movies/shows, mark something as watched with a rating (show + season level for TV), write an optional review, record the watch date, add/remove items from a watchlist, and view their own history (diary) in chronological order.

## Tech Stack

- **Frontend:** Next.js 16 (App Router), React 19, TypeScript (strict mode)
- **Styling:** Tailwind CSS 4
- **Backend/DB:** Supabase (Postgres + Auth + Row Level Security)
- **Auth methods:** Email/Password + Google OAuth (via Supabase Auth)
- **External data source:** TMDB API (movie/show/season metadata, posters, cast, descriptions)
- **Deployment:** Vercel

> ⚠️ This repo runs Next.js 16. Per `AGENTS.md` (auto-regenerated by `next dev` on every run), this version may differ from training-data Next.js APIs/conventions, so `node_modules/next/dist/docs/` must be checked before writing code.

### High-level data model (detailed schema to be finalized in the Plan phase)

- `profiles` — 1:1 with Supabase `auth.users`, holds public profile info (username, avatar). **Feature 8 adds** `top_movie_ids int[]` (≤4, ordered), `top_show_ids int[]` (≤4, ordered), `now_watching_show_id int` (nullable) — all TMDB ids.
- `movie_logs` — user_id, tmdb_movie_id, rating (0.5–5), review (nullable text), watched_date, rewatch (bool)
- `show_logs` — user_id, tmdb_show_id, rating (0.5–5, overall show rating), review (nullable text)
- `season_logs` — user_id, tmdb_show_id, season_number, rating (0.5–5), review (nullable text), watched_date
- `watchlist` — user_id, tmdb_id, media_type (`movie` | `tv`), added_at

RLS: writes (`insert`/`update`/`delete`) on every log table are always scoped to `auth.uid() = user_id` — a user can never modify another user's row. Reads are mixed: `movie_logs`, `show_logs`, and `season_logs` are publicly readable (rating + review + username, so every user's review shows up under the relevant title, visible even to guests) — this is the one deliberate exception to "no social visibility." `profiles` is publicly readable for `username` only in the MVP. **Feature 9 widens this:** `avatar_url` and the Feature 8 showcase columns become publicly readable too (via column grants + a `security_invoker` `profiles_public` view), and a public `/user/[username]` page lists everything a given user has logged — the MVP's "no full log listing" rule is intentionally dropped.

Features added after the MVP was reached. Listed in `todo.md` numbering. Not yet

### Feature 8 — Profile page: favourites showcase, now-watching, change password

The private `/profile` dashboard gains an editable **showcase** (managed from
`/settings`), and `/settings` gains a **change-password** form.

- **Top 4 movies / Top 4 shows** — the user searches TMDB and picks up to 4
  movies and up to 4 shows, in a chosen order (Letterboxd "4 favourites"
  semantics: any title, independent of whether it's been logged/watched).
  Stored as `profiles.top_movie_ids` / `profiles.top_show_ids` (ordered
  `int[]`, each ≤ 4 positive TMDB ids).
- **Currently watching** — the user picks a single show from TMDB search as
  their "currently watching"; they can change or clear it. Stored as
  `profiles.now_watching_show_id` (nullable positive TMDB id). No auto-derivation
  (screenlog has no episode-level progress).
- **Change password** — a form on `/settings` (not `/profile`). Requires the
  user to re-enter their current password (re-authenticate, then
  `supabase.auth.updateUser({ password })`). Hidden for accounts with no
  password (Google-OAuth-only) — those show a short note instead.

### Feature 9 — Public profiles

`/user/[username]` becomes a public page visible to anyone (guests included),
showing: avatar + username, movie/show/watchlist counts, the Feature 8 showcase
(top-4s + currently-watching), and a **browsable grid of every movie and show
the user has logged** (with rating, linking to the title page). "See all" links
lead to paginated `/user/[username]/films` and `/user/[username]/shows`.

This deliberately drops the MVP rule that "no page lists everything a user
logged". The existing private `/profile` stays as the owner's editable
dashboard; `/user/[username]` is the read-only public view.

### Discover, Follow, Activity feed

Three features, built in this order. Realtime notifications (first type:
"X followed you") are a **separate later spec** that builds on Follow — not
part of this one.

#### Discover page

The home page is splitting into personal content (yours + people you follow)
and browse content (same for everyone). Browse content moves to a new
`/discover` route; no new logic, only relocation of existing sections.

| Page | Sections |
|---|---|
| `/` (signed in) | Search, Pick up where you left off, Activity feed (once built) |
| `/` (guest) | Hero + search + sign-up prompt, then Popular movies and Popular TV shows rows so the page isn't empty |
| `/discover` (anyone) | Mood picker, Popular movies, Popular TV shows (the seasonal mood section from the mood spec was never built; it would land here if added later) |

The navbar gains a `Discover` link next to `Search`, visible to guests too.

#### Follow users

- **Open, one-way follow** (Letterboxd model): following is instant, no
  request/approval, no private accounts.
- **Where:** a Follow / Following button on `/user/[username]` (hidden on your
  own profile) and on each row of the follower/following modals. Guests don't
  see the button at all.
- **Counts + lists:** `/user/[username]` shows follower and following counts,
  visible to anyone including guests. Clicking a count opens a **modal on the
  same page** (not a separate route) listing those users: avatar, username
  (links to their profile), Follow button.
- Users are found via the existing People mode on `/search`
  (`?mode=people`) and the username links on review lists — no new user
  search is needed.

#### Activity feed

- Signed-in home page section listing recent activity from the people you
  follow, as **one combined stream** sorted newest-first:
  - movie logs, show logs, season logs (`created_at`): "**user** watched
    *Title*" (or "rewatched"), rating stars if present, first ~2 lines of the
    review if present; season logs read "*Show* — Season N"
  - watchlist additions (`added_at`): "**user** added *Title* to their watchlist"
  - new followers of **the viewer** (`follows.created_at` where
    `following_id` = viewer): "**user** followed you" — from anyone, whether
    or not the viewer follows them back. Other people's follows ("X followed
    Y") and the viewer's own follows are not shown.
- **Vertical list**, not a `MediaRow`: small poster, avatar, the line above,
  relative time ("2h ago"). Poster/title link to the title page; username
  links to the profile.
- **10 items** on load, total across all activity types (not 10 per type). A
  "Show more" button loads the next 10. No infinite scroll, no realtime.
- Editing a log does not bump it — ordering is by creation time only.
  Removing a watchlist item removes that activity (no history is kept).
- **Watchlists become publicly readable** (explicit decision, 2026-10-30) —
  needed so the feed can read followed users' watchlists. This applies to
  every user's existing watchlist. Showing watchlists on profiles was added
  later — see [Public watchlists on profiles](#public-watchlists-on-profiles).
- Empty state (no followed-user activity and no new followers yet): short message linking
  to People search (`/search?mode=people`) to find users to follow. Guests
  don't see the feed at all.
- Known limitation, accepted for v1: one user adding many watchlist items in
  a row can fill the feed. Grouping consecutive watchlist adds is deferred.

### Diary grid view

The diary (`/diary`) and the see-all lists (`/user/[username]/films`,
`/user/[username]/shows`) gain a **grid / list view toggle**, Letterboxd-style.

- **Grid (default):** a poster grid with small read-only rating stars under
  each poster. No title text, date or review — the title is the poster's
  alt text and tooltip. 3 columns on mobile, 4 from `sm` up. Unrated entries
  show the poster only; a missing poster shows the title as a placeholder.
  Each poster links to the title page.
- **List:** the current row layout (poster, title, date, stars, review),
  unchanged.
- **Toggle:** two icon links (`LayoutGrid`, `List`) next to the page title,
  each with an accessible name; the active one is marked `aria-current`.
  Hidden when there are no entries.
- **State lives in the URL:** no `view` param = grid, `?view=list` = list,
  any other value falls back to grid. On the see-all pages, pagination links
  keep the current view and switching view keeps the current page (page size
  stays 24, which divides evenly into 3 and 4 columns).
- **Width** stays `max-w-2xl` in both views.
- **Out of scope:** pagination on `/diary`; DB-level pagination (the lists
  still fetch every entry and slice in memory).

#### Acceptance criteria

- [ ] `/diary` opens in grid view: Movies and Shows sections each show a poster grid with stars under rated entries.
- [ ] Clicking the list icon switches `/diary` to the current row layout and the URL to `/diary?view=list`; clicking the grid icon returns to `/diary`.
- [ ] `/user/[username]/films` and `/shows` open in grid view and have the same toggle.
- [ ] On a see-all page, Next/Previous keep the view (`?page=2&view=list`), and switching view keeps the page.
- [ ] An unknown `view` value renders grid; the toggle is hidden when a list is empty.
- [ ] Toggle links are keyboard-reachable, have visible focus and accessible names.

### Copy profile link

A share shortcut on profiles: one click copies the profile's URL so it can be
pasted anywhere.

- **Where:** an icon button (lucide `Link`) in the `/user/[username]` header,
  next to the username alongside the Settings / Follow controls. Visible to
  everyone — owner, other users and guests. Styled like the Settings icon.

- **Out of scope:** native share sheet, rich link previews (Open Graph), short

#### Acceptance criteria

- [ ] A guest, another signed-in user and the owner all see the copy button on `/user/[username]`.
- [ ] Clicking it puts the profile's absolute URL on the clipboard and shows a success toast.
- [ ] If the clipboard write fails, an error toast is shown.
- [ ] The button is keyboard-reachable, has visible focus and the accessible name "Copy profile link".

### Watchlist type filter

The full watchlist page mixes movies and shows; a filter lets the viewer see
just one type ("what movie do I watch tonight?"). The diary and see-all lists
already split Films / Shows — the watchlist is the only mixed list. No
migration.

- **Where:** `/user/[username]/watchlist` only, for owner and visitors alike.
  The profile's Watchlist preview (4 items) stays unfiltered.
- **Control:** three text links — **All**, **Movies**, **Shows** — next to the
  page title, styled like the diary view toggle (bordered segmented group,
  active one marked `aria-current`). Hidden when the watchlist is empty.
- **State lives in the URL:** no `type` param = All, `?type=movie` = movies,
  `?type=tv` = shows; any other value falls back to All. The values match
  `mediaType`, so filtering is a plain equality check.
- **Filtering:** server-side, in memory, on the items `getWatchlistItems`
  already returns. Order stays newest-added first.
- **Owner removals:** the owner can still remove items in every filter. The
  grid keeps local state from its initial items, so it is keyed by the
  filter to reset when the filter changes.
- **Empty states:** a filter with no matches shows "No movies on the
  watchlist yet." / "No shows on the watchlist yet." (owner: "…on your
  watchlist yet."). The whole-watchlist empty message is unchanged.
- **Out of scope:** per-type counts on the filter links, sorting options,
  filter on the profile preview, pagination.

#### Acceptance criteria

- [ ] `/user/[username]/watchlist` shows All / Movies / Shows links next to the title for the owner, other users and guests.
- [ ] Clicking Movies changes the URL to `?type=movie` and shows only movies; Shows → `?type=tv`, only shows; All → no param, everything.
- [ ] An unknown `type` value renders All; the filter links are hidden when the watchlist is empty.
- [ ] A filter with no matching items shows its own empty message.
- [ ] The owner can remove items while a filter is active; switching filter afterwards shows the correct items.
- [ ] Filter links are keyboard-reachable, have visible focus, and the active one has `aria-current`.

### Show status: completed / dropped

A show log currently means "I finished this show" (its date field is already
labelled "Date finished"). This adds the one exception: a show the user gave
up on. It also lets the planned stats page count watch hours honestly.

- **Data:** migration `0017` adds `show_logs.status text not null default
  'completed'` with a check constraint `status in ('completed', 'dropped')`.
  Existing rows become `completed`. Existing RLS/grants cover the new column.
  Movies and seasons are unchanged.
- **UX principle:** Completed is the common case and stays one click away;
  Dropped is rare and lives one step deeper (progressive disclosure). The
  log card keeps a single pill, in the same place as movies' and seasons'
  "Watched" pill.
- **Log card pill (show page, card and modal):** the show's "Watched" pill
  becomes a three-state pill, same toggle behaviour and `aria-pressed`:
  - No log: "Mark as completed" (lucide `CircleCheck`, muted). Clicking it
    creates a bare `completed` log dated today.
  - Completed: "Completed" (`CircleCheck`, accent gold — today's watched
    style).
  - Dropped: "Dropped" (`CircleSlash`), with the same pressed anatomy as
    Completed (tinted border + fill + text) in the neutral foreground
    colour, so it reads as selected. Not red (it isn't an error or a
    destructive action, and the card's Delete button is red) and not gold
    (that reads as an achievement). Icon + text, never colour alone.
  - Clicking a pressed pill removes the log with today's watched rules:
    refused (inline error) while the log has a rating or review.
  - Toasts: "Marked as completed" / "Removed".
  - Movies and seasons keep their "Watched" pill as is.
- **Log modal:** an "I dropped this show" checkbox under the date field,
  with the hint "Stopped watching before the end." It is checked for a
  dropped show and saved with the rest of the form (**Save**); unticking it
  and saving makes the show completed again. While ticked, the date field
  is labelled "Date dropped" (live, before saving); otherwise "Date
  finished". To log a show as dropped straight away: Rate & review → tick →
  Save.
- Rating a show when it has no log creates the log as `completed` (the
  column default), as happens with "watched" today.
- **Where "Dropped" shows:** a small "Dropped" label next to the show's
  entry in the diary (`/diary`, grid and list), the profile's shows list
  (`/user/[username]/shows`) and its Shows preview, and in the show page's
  public review list. Completed shows get no label (it's the default).
- **Activity feed:** a show log reads "**user** completed *Show*" or
  "**user** dropped *Show*" (current status of the row). Movie and season
  logs keep "watched".
- **Validation:** the show log schema accepts only `completed` / `dropped`
  (Zod enum, default `completed`); anything else is rejected without
  writing.
- **Tests:** existing unit and e2e tests that refer to the show "Watched"
  pill / "watched" feed text for shows are renamed and updated to the new
  labels; new tests cover the pill states, the checkbox and the feed
  wording.
- **Out of scope:** "Watching" / "On hold" statuses (the profile's Now
  watching covers watching), statuses for movies or seasons, filtering by
  status, a separate feed event when the status changes.

### Stats page

A per-user numbers page, "Year in Review"-style: how much they watched, when,
and how they rated it. Public like the rest of the profile. No migration.

- **Route:** `/user/[username]/stats`, visible to everyone (owner, other users,
  guests); unknown username → 404. The profile links to it with a full-width
  "Stats" card under the stats strip (chart icon, "Watch time, activity and
  ratings" subtitle, chevron) — a plain text link read as a caption, not a
  destination.
- **Period (URL state):** no `year` param = the current year, `?year=2024` = that
  year, `?year=all` = all time. Any other value falls back to the current
  year. A selector next to the title lists the current year, every other year
  that has a log (newest first) and "All time"; the active one is marked
  `aria-current`. A log belongs to the year of its `watched_date`.
- **What counts:** every row in `movie_logs`, `season_logs` and `show_logs` is
  one entry. There is one row per user and title (season), so each title
  counts once, in the year of its `watched_date`. When rewatch support
  (several logs per title) lands, revisit this: each watch should probably
  count as its own entry, in its own year.
- **Metrics:**
  1. **Totals:** Films, Shows and Hours watched for the period.
     - **Films** = movie logs in the period.
     - **Shows** = number of *distinct* shows (`tmdb_show_id`) with a season
       or show log in the period — logging 3 seasons of a show and rating
       the show itself counts as 1. (The profile stats strip keeps its
       current count; only this page counts distinct shows.)
     - **Hours** = movie runtimes (TMDB `/movie/{id}`, already fetched for
       the diary) + show runtimes, rounded down to whole hours:
       - A **completed show log** means the whole show was watched: it adds
         every aired episode's runtime across all regular seasons (season
         0 / specials and episodes without an air date or airing after
         today are excluded).
       - A **dropped show log** (`show_logs.status = 'dropped'`, migration
         0017) adds no hours by itself — only that show's season logs
         count.
       - **Season logs** add that season's episode runtimes — unless the
         same show also has a *completed* show log in the period, which
         already covers every season (no double counting).
       - Episode runtimes come from TMDB season details, fetched with
         `append_to_response=season/1,…` (up to 20 seasons per request).
         Missing runtimes count as 0.
       - Product rule: a completed show log means "I finished this show";
         a show given up on is marked dropped, with the watched seasons
         logged per season.
     - Dropped shows still count towards **Shows** (they were watched in
       part).
     - Under the strip, the watch time is split by type, one row each:
       "Films — 1 day, 2 hours and 10 minutes", "Shows — 12 days, 2 hours
       and 37 minutes". Days / hours / minutes with zero units left out; no
       months (they vary in length) and no seconds (TMDB runtimes are whole
       minutes). A type with no watch time is left out; the whole breakdown
       is hidden when both are zero. Hours stays the combined total.
  2. **Activity chart:** a bar chart of entries per month (Jan–Dec) for a
     year; per year (oldest → newest) for all time. Empty months/years show
     a zero-height bar so the axis stays continuous.
  3. **Rating distribution:** a histogram of ratings 0.5 → 5 (ten bars) over
     the period's rated entries; unrated entries are left out.
- **Charts:** plain HTML/CSS bars styled with the app's tokens — no chart
  library. Each chart also exposes its numbers to screen readers (labelled
  bars or a visually hidden table), and the values are readable without
  hovering. Hover, keyboard focus or a tap on a bar shows a tooltip above
  that bar with its full name and the films / TV split ("March 2026 · 7
  entries · 4 films · 3 TV" — TV counts season and show logs). Each chart is
  one tab stop; arrow keys / Home / End move between bars.
- **Computation:** a pure function turns the logs (+ resolved runtimes) into
  the three metrics for a period; it is unit-tested. TMDB lookups go through
  `tmdbFetch` (daily cache) and a failed lookup drops only that runtime, never
  the page.
- **Empty state:** a period with no entries shows "No entries in {period}."
  instead of the metrics; the selector stays visible.
- **Out of scope:** genres, decades, people (actors/directors), average
  rating, top-rated / first-last posters, review counts, sharing
  or images, per-day charts.

#### Acceptance criteria

- [ ] `/user/[username]/stats` opens for a guest, another user and the owner, showing the current year; an unknown username returns a 404.
- [ ] The selector lists the current year, every year with a log, and All time; choosing one updates the URL (`?year=2024`, `?year=all`) and all three metrics.
- [ ] An invalid `year` value shows the current year.
- [ ] Films equals the period's movie logs; Shows equals the distinct shows with a season or show log (3 season logs + 1 show log of one show → 1).
- [ ] Hours equals movie runtimes plus, per show, all aired regular-season episodes if it has a completed show log, otherwise (no show log, or a dropped one) only the logged seasons' episodes — rounded down, never counting a season twice.
- [ ] A dropped show with no season logs adds 0 hours but still counts as 1 Show.
- [ ] Under the strip, film and show watch time are shown separately as days, hours and minutes (e.g. 17,437 min → "12 days, 2 hours and 37 minutes"), zero units and zero-time types left out; Hours is their combined total.
- [ ] The activity chart has 12 monthly bars for a year and one bar per year for all time, including zero bars.
- [ ] The rating histogram has ten bars (0.5–5) and ignores unrated entries.
- [ ] A period with no entries shows the empty message.
- [ ] Chart values are available to screen readers; selector links are keyboard-reachable with visible focus.
- [ ] The profile's "Stats" card opens the page; the layout fits a 375px-wide screen with no horizontal scroll.

### Review likes

> **Status: agreed (2026-11-03)** — open questions settled (see "Decisions"
> below); only the profile entry point for liked reviews is left to subtask 8.

- **Goal:** let people like each other's reviews, see who liked one, surface
  likes in the activity feed, sort a title's reviews by popularity, and list
  a user's liked reviews.
- **Data model (decided):** reviews stay where they are — the `rating` /
  `review` columns of `movie_logs`, `show_logs` and `season_logs` (one log
  row = one review; matches Letterboxd's log-entry model and future rewatch
  support). Likes go in **one** new table, migration
  `0018_review_likes.sql`:
  - `review_likes (id, user_id → auth.users, movie_log_id → movie_logs,
    show_log_id → show_logs, season_log_id → season_logs, created_at)`;
    the three log FKs are nullable with a check that **exactly one** is set
    (`num_nonnulls(...) = 1`) and `on delete cascade`, so deleting a log
    deletes its likes.
  - One like per user per review: a unique index per FK column
    (`(user_id, movie_log_id)` etc.).
  - Rejected: a polymorphic `(log_type, log_id)` pair — no real FK, likes
    of deleted logs would be orphaned. Rejected: moving reviews to their own
    table — touches every log form/action/feed for no gain.
- **RLS:** likes are publicly readable (anon + authenticated, like logs);
  a user can insert and delete only rows with `user_id = auth.uid()`.
  Liking your own review is blocked — in the action and in the
  insert policy (the policy checks the referenced log's `user_id`).
- **What can be liked:** only log rows with written review text. Rating-only entries show no heart.
- **Like button:** heart + count on every likeable review in `ReviewList`
  (movie, show and season pages). Toggling is optimistic and rolls back
  with an error toast on failure. `aria-pressed`, accessible name "Like
  {username}'s review" / "Unlike …". On your own review: count only, no
  button. Guests see the count; the heart links to `/login`.
- **Likers modal:** clicking the count (when > 0) opens a dialog listing
  who liked it — newest first, avatar + username + Follow button, the same
  look and behaviour as the followers/following modal on the profile
  (`profile-stats.tsx`; extract a shared user-list dialog if it keeps the
  code simpler).
- **Activity feed:** a new event source — likes by people the viewer
  follows: "**user** liked **reviewer**'s review of *Title*" (season reviews:
  "*Show* — Season N"), linking to the title page; ordered by
  `review_likes.created_at` with the existing keyset cursor (`key`
  `review_like:<id>`). Also "**user** liked your review of *Title*" from
  anyone (followed or not), like "followed you". Unliking removes the event.
- **Popular sort:** title/season pages get a **Recent | Popular** switch
  above the reviews; Recent is the current order and the default, Popular
  orders by like count (ties → newest). State in the URL
  (`?reviews=popular`) so it's linkable and works without JS.
- **Liked reviews page:** `/user/[username]/likes`, public, the reviews
  that user liked, newest like first: poster, title, reviewer, stars,
  review excerpt, link to the title page; same pagination/empty-state
  pattern as the other profile list pages. **How the profile links to it is
  decided in subtask 8** with a ui-ux-pro-max evaluation (a card like
  "Stats" is one candidate) and the user's approval.
- **Editing / clearing:** editing a review keeps its likes. Clearing the
  review text (keeping only a rating) keeps the rows but hides the heart;
  deleting the log cascades. Known gap, accepted for now (2026-11-04): those
  kept rows could still surface in the feed, the liked reviews page and the
  popular sort — a trigger deleting them was considered and deferred.
- **Out of scope:** notifications (no notification system yet — its own
  task later), liking comments, like counts on profile cards, liking
  rating-only entries.

#### Decisions (settled 2026-11-03)

1. A user can't like their own review.
2. Only entries with written review text are likeable.
3. Guests see the count; the heart links to `/login`.
4. The feed also shows "X liked your review" from people you don't follow.
5. The profile's entry point to liked reviews is designed in subtask 8 with
   ui-ux-pro-max, then approved by the user.

#### Acceptance criteria

- [ ] Migration 0018 creates `review_likes` with exactly-one-FK check, per-FK unique indexes, cascade delete and RLS (public read, own insert/delete).
- [ ] A signed-in user can like and unlike someone else's review on movie, show and season pages; the count updates immediately and survives a reload.
- [ ] Liking twice is impossible (unique index) and a failed toggle rolls back with an error toast.
- [ ] Own reviews can't be liked (count only); rating-only entries show no heart; guests see the count and the heart links to `/login`.
- [ ] The feed shows "X liked your review of Title" from anyone, followed or not.
- [ ] Clicking a non-zero count opens the likers modal (newest first, profile links, Follow buttons) with loading/error/empty states, closable with Esc and the close button.
- [ ] The activity feed shows likes by followed users with correct wording and links, paginates with the existing "Show more", and an unliked review disappears from it.
- [ ] Recent / Popular reorders a title's reviews (likes desc, ties newest), is reflected in `?reviews=`, and Recent stays the default.
- [ ] `/user/[username]/likes` lists that user's liked reviews newest-first for guests and users; unknown username → 404; empty state when none.
- [ ] Deleting a log removes its likes everywhere (counts, modal, feed, liked page).
- [ ] Heart button is keyboard reachable with visible focus, `aria-pressed`, ≥24px target; everything fits 375px with no horizontal scroll.
